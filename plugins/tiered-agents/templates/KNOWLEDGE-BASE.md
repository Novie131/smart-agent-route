# 知識庫怎麼組織

## 目錄結構

```
<你的資料夾>/
└── claude-memory/
    ├── MEMORY.md      ← 常駐索引。每次自動注入,預算 40 行
    ├── topics/        ← agent 自己累積的知識
    └── kb/            ← 你自己放的筆記與參考資料
```

建立方式:

```bash
mkdir -p <你的資料夾>/claude-memory/{topics,kb}
cp templates/MEMORY.md <你的資料夾>/claude-memory/MEMORY.md
```

## 為什麼 topics/ 和 kb/ 要分開

**寫入者不同,信任程度也不同。**

`topics/` 是 agent 自己寫的——它會過期、會有誤解、偶爾會寫錯。你隨時可以刪掉整個目錄重來,損失有限。

`kb/` 是你自己的東西——agent 不該改它。這條界線讓你在整理 `topics/` 時可以放心大膽地砍。

分開還有一個好處:當檢索結果彼此矛盾時,你一眼就知道該信哪邊。

## kb/ 怎麼放

**直接丟 `.md` 進去就能用,不需要任何前處理。** 沒有索引步驟、沒有 embedding、沒有重建流程。

幾個讓檢索變準的習慣:

**檔名寫成人話。** `部署流程-正式環境.md` 比 `deploy-v2-final.md` 好找。librarian 會搜檔名,檔名就是最便宜的索引。

**每個檔開頭寫兩三行「這篇在講什麼」。** Grep 命中之後,這幾行決定它要不要繼續讀下去。

**一個檔一個主題。** 三千行的萬用筆記,檢索出來會塞爆呼叫者的 context——這正好抵銷掉 librarian 存在的意義。

**中英文都寫進去。** 技術術語在標題或開頭同時放中英文,兩種搜法都能命中。這是投報率最高的一個小動作。

## 要不要做真正的向量 RAG

以個人知識庫的規模來說,**通常不需要**,而且常常更差。

| 規模 | 建議 |
|---|---|
| 幾十篇 | `MEMORY.md` 索引就夠,連 librarian 都不太需要 |
| 幾十到幾百篇 | **現在這套**:索引 + librarian 的 agentic search |
| 上千篇,或大量 PDF、掃描檔、長逐字稿 | 這時才值得考慮向量檢索 |

不建議在這個規模上向量的理由:

- **要多一整套基礎設施**——embedding 服務、向量庫、重新索引的流程。而且每次改筆記都要重跑。
- **檢索失敗很難除錯。** grep 沒中,你看得到搜了什麼詞、為什麼沒中,改一下就好。向量沒中,你只能猜。
- **切塊會破壞結構。** Markdown 的標題層級本身就是語意結構,切成 chunk 之後這層資訊就沒了。
- **它也要花 token。** embedding 不免費,而你的初衷是省。

反過來說,agentic search 有一個向量做不到的優勢:**它會反覆嘗試**。第一個詞沒中就換同義詞、換語言、改搜檔名。這種「換個角度再找一次」的行為,固定的向量查詢做不到。

真的長到需要向量的那天,現在這個結構也不用改——`kb/` 底下的 markdown 本來就是最好的語料格式。到時候加一層,不是重來。
